## Commands

```bash
# Build
dotnet build MonthSpendings.sln

# Run (development)
dotnet run --project MonthSpendings/MonthSpendings.csproj

# Apply migrations (runs automatically on startup — no manual step needed)
dotnet ef database update --project Infrastructure --startup-project MonthSpendings

# Add a migration
dotnet ef migrations add <MigrationName> --project Infrastructure --startup-project MonthSpendings
```

There are no test projects currently.

## Architecture

Clean Architecture with 4 layers:

- **Domain** — entity models only, no dependencies
- **Application** — use cases, DTOs, interfaces, mappers; depends on Domain
- **Infrastructure** — EF Core `AppDbContext`, repositories, migrations, external service clients; depends on Application + Domain
- **MonthSpendings** — ASP.NET Core 10 Web API entry point; depends on Application + Infrastructure

A fifth project, **EnableBanking**, wraps the third-party open-banking SDK.

All DI registrations live in `MonthSpendings/Program.cs`.

## Key Patterns

### Use Case pattern
Every business operation is a dedicated class implementing an interface, e.g. `ICreateBudgetUseCase` → `CreateBudgetUseCase`. All return `CaseResult<T>`. Failures return `CaseResult<T>.Error(Messages.BudgetNotFound)` — the text from the generated resx class, already in the request language — optionally with an `ErrorType` (`ProRequired`, `Conflict`, `Locked`, `Unauthorized`; default `Failure`). Formatted texts: `string.Format(Messages.X, args)`. Never inline strings. Controllers derive from `ControllerBase` and return failures as `StatusCode((int)result.ErrorType, result.ErrorMessage)`.

**Exceptions:** use cases do **not** wrap their body in `try/catch`. `CaseResult.Error` is only for expected outcomes; anything unexpected bubbles up to `MonthSpendings/Exceptions/GlobalExceptionHandler.cs`, which returns a generic 500 ProblemDetails with the request's `traceId` (it does not log — Serilog request logging already logs the exception with UserId + TraceId in the request's `responded 500` line) — the client shows its own translated message. Only catch an exception you can actually handle (e.g. a failed push must not fail the request). An uncommitted `BeginTransactionAsync()` is rolled back automatically when the request's `DbContext` is disposed; use a transaction only for multiple `SaveChanges` calls.

### Localization (en / bg / es)
- **Error contract:** HTTP status + plain message string (translated via `Accept-Language` → `UseRequestLocalization`; unsupported → English). `ErrorType` values *are* the HTTP statuses; the client opens the ProGate on **402** (`ErrorType.ProRequired`). Validation/unhandled errors stay ProblemDetails.
- **Adding an error:** add the entry to all three `Messages*.resx` files (PascalCase, area-prefixed: `BudgetNotFound`; shared ones unprefixed: `TooManyRequests`) and use `Messages.Xxx`. Validation attributes use `ErrorMessageResourceType = typeof(Messages), ErrorMessageResourceName = nameof(Messages.Xxx)`.
- **Typed resources:** `Resources/Messages.Designer.cs` (the public `Application.Resources.Messages` class) is generated by Visual Studio's `PublicResXFileCodeGenerator` when `Messages.resx` is saved, and is checked in. `dotnet build` does not regenerate it — after editing the resx outside VS, open and save it in VS (or right-click → Run Custom Tool). Keep entry names valid C# identifiers.
- **Push notifications:** add `PushXxxTitle`/`PushXxxBody` entries to all three resx files and call `IPushNotificationService.SendLocalized(recipients, nameof(Messages.PushXxxTitle), nameof(Messages.PushXxxBody), dto, args...)`. It takes keys (not `Messages.X` texts) because each recipient gets the text in *their* language (`AppUser.Language`), not the request's. Never pass hardcoded title/body text.
- **Request culture:** resolved by the built-in `UseRequestLocalization` (`?lang=`, then `Accept-Language`; `bg-BG` → `bg`, unsupported → `en`). After it, `CultureInfo.CurrentUICulture.TwoLetterISOLanguageName` is always a supported language — don't re-parse tags by hand. `SupportedLanguages` only holds the list.
- **User language:** `AppUser.Language` (`en`/`bg`/`es`). Set by the client via `PUT /api/user/language` (other values → `user.unsupported_language`); new users default to the request culture.
- **Privacy page:** `/privacy-policy?lang=bg` — text lives in `Pages/PrivacyPolicyContent.cs`.

### Logging (Serilog, structured)
- **Where:** use cases log every failure **right before** `return CaseResult<T>.Error(...)`, in English, with IDs as template properties (`"Budget {BudgetId} not found for user {UserId} on delete", budgetId, userId` — never string interpolation). Controllers don't log; the request log (`HTTP {Method} {Path} responded {StatusCode}`, enriched with `UserId`) adds endpoint + status.
- **Levels:** `Debug` = high-volume routine reads ("Retrieved 12 budgets"). `Information` = expected outcomes, incl. rejections (not found, needs Pro, wrong password, success events). `Warning` = abnormal or suspicious (permission violation, missing user behind a valid token, token reuse, lockout, inconsistent data). `Error` = exceptions, with the exception object.
- **Never log** tokens, passwords, emails or other personal data — log the user id instead. Never log the translated `ErrorMessage`.
- **Sinks:** console and the Postgres `Logs` table both get Information+ in every environment (EF query logs stay out in production via the `Microsoft.EntityFrameworkCore.Database.Command: Warning` override). No automatic cleanup of the `Logs` table.

### Unit of Work + Repository
`IUnitOfWork` in Application exposes all repositories and wraps DB transactions (`BeginTransaction` / `CommitTransaction` / `RollbackTransaction`). Repositories are transient and only accessed through the UoW.

### Mappers
Extension methods convert between entities and DTOs, e.g. `budget.ToDto()`, `budgetDto.ToEntity()`. Located in `Application/Mappers/`.

## Database

PostgreSQL via EF Core 10. Connection strings:
- **Development:** `localhost:5432` (see `appsettings.Development.json`)
- **Production:** Neon serverless PostgreSQL (see `appsettings.json`)

Migrations are applied automatically at startup (`Program.cs`). Migration files live in `Infrastructure/Migrations/`.

## Background Service

`InactivityNotificationBackgroundService` runs every 60 s and sends a localized "we miss you" push at ~09:00 user-local time (`AppUser.Timezone`) to users inactive for 24 h+.

## Authentication

JWT Bearer tokens. `UserService` extracts `UserId` from JWT claims and is scoped. `RequireHttpsMetadata = false` in development. Token lifetime is 100 years (by design). Google OAuth stores `GoogleId` and `GooglePhotoAddress` on `AppUser`.

## External Integrations

- **EnableBanking API** — requires `EnableBanking:AppCertPath` and `EnableBanking:AppKeyId` in config; certificate is included for production
- **Expo push notifications** — `IPushNotificationService` via `Expo.Server.SDK`
- **Swagger** — enabled in development at `/swagger`
